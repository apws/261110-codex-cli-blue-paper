== Request and current status

Falken prefers the terminal Codex interface and wants his own messages to stand out: light-blue paper with dark ink, both while typing and after submission. He asks for a local implementation plan, including fetching Rust tools, realistic recompilation effort, safety, rollback and reapplication after Codex updates.

*This is a plan, not an installation.* Only documentation and read-only inspection have been performed for this request. Rust has not been installed, Codex has not been rebuilt, and no launcher, terminal profile or installed executable has been replaced.

The earlier `Settings -> Appearance` advice concerned the desktop app and was inappropriate for this CLI session. The CLI's recorded syntax theme is `github`. Its `/theme` mechanism accepts custom `.tmTheme` files, but the inspected submitted-message and composer fills are computed separately in Rust. A custom syntax theme alone does not implement this request.

|Custom launch |Use an explicit `codex-blue` wrapper pointing to a separately built and versioned executable.

Implement a small local feature with our own wrapper-controlled environment variables, provisionally `CODEX_BLUE_PAPER`, `CODEX_BLUE_PAPER_BG` and `CODEX_BLUE_PAPER_FG`. *These are proposed additions in our patch, not existing upstream Codex settings.* Parse the two colors once per process, handle invalid input predictably, and keep stock rendering available when the feature is disabled. Do not add invented keys to the upstream `config.toml` schema.

The core color change should be tens of lines. Robust handling of styled spans, focused tests, build automation, packaging and update checks will be a larger amount of work. Calling the entire deliverable a two-line tweak would understate it.

=== Snapshot recovery, recent changes and the large-directory review

Falken was understandably surprised that deleting many Snapper snapshots appeared to return only about 1 GiB initially, followed later by almost 488 GiB available space. He reported a recent large CachyOS update, including Plasma 6.8, and a recent move of virtual machines to a USB3-connected 2 TB disk mounted at `/_/vbox`. The update/version and migration history here are Falken's account; they were not reconstructed from package or migration logs.

The likely explanation is retained historical data followed by delayed reclamation, rather than newly created disk capacity:

. A snapshot shares existing file blocks initially. Subsequent overwrites and deletions can leave old blocks referenced by snapshots.
. A large OS update can therefore leave older package/library contents retained by system snapshots.
. *If the former VM directory belonged to a snapshotted subvolume*, moving its files to another disk can remove the live files while snapshots still retain their old blocks. A snapshot of a different subvolume would not retain those VM files; do not assume every root snapshot includes the separately mounted home directory.
. Deleting old snapshots removes those historical references. Blocks become reclaimable when no remaining reference needs them, and subvolume cleanup proceeds in the background. A small initial free-space increase followed by a much larger increase is consistent with this behavior.

This is a supported explanation of the mechanism and a plausible account of this session, not proof of exactly how many bytes came from the OS update, the VM move or any particular snapshot. The deleted snapshots were not measured before removal. Deleting ordinary old Snapper restore points is a normal operation; its direct consequence is losing those older rollback points. The observed space jump alone is not evidence of corruption.

=== Prevent the build cache from becoming another snapshot surprise

Before the first Rust build, inspect the actual Snapper configuration and which subvolumes contain the planned source, toolchain and Cargo target/cache directories. Git ignore rules do not exclude files from filesystem snapshots. Repeated snapshots of a changing compiler cache can retain earlier artifacts long after an ordinary cleanup or rebuild.

Keep our small source patch, scripts and build manifests backed up. Consider placing regenerable Cargo targets/download caches outside the intended snapshot scope, for example in a dedicated nested subvolume *after reviewing the existing backup/snapshot layout*. Btrfs snapshots do not recursively include nested subvolumes; this is a layout decision to verify, not a change made by this plan. Do not silently change Snapper policy or remove the remaining restore point.

This extra setup is part of implementing codex-blue responsibly, not a reason to move the entire development workspace or borrow the VM drive unnecessarily. Measure actual build-cache growth and record it with the first build timing.

== Implementation steps

=== 1. Create a separate local build workspace

Keep this plan in the KiCad chat's documentation history. Put implementation outside the KiCad repository, provisionally under `/home/falken/_/wrk/ver/261110-codex-cli-blue-paper/`, after checking that the location is available and suitable.

Keep a small Git repository for our patch, scripts, color profile, tests and handover. Store the pinned upstream checkout and large Cargo artifacts in ignored subdirectories or a dedicated build filesystem. Record source commit, patch checksum, compiler/target, Cargo.lock hash, build profile, binary checksum and test results in a per-build manifest. Keep source attribution and applicable license notices.

Inventory the actual launcher, native package, resource directory and any helper executables before designing the custom package. A bare copied binary may not reproduce the installed package's helper/resource lookup. Verify the custom launcher and helper layout rather than assuming a successful `--version` proves normal operation.

=== 2. Fetch Rust with an isolated user-local installation

Download the installer from the official Rust rustup distribution, retain the downloaded installer and its checksum, inspect the invocation, and run it as the ordinary user. Use dedicated `RUSTUP_HOME` and `CARGO_HOME` directories inside our local build area and `--no-modify-path`; invoke their binaries explicitly from the build script. Use the minimal installer profile and the source-pinned toolchain, then provision the components declared by the checkout.

For the inspected baseline this means Rust `1.95.0`, not whatever the generic installer currently considers latest. Future releases must use their own declared toolchain. Record all installed versions.

Do not use `sudo` for Rust or the custom Codex build. Inspect native-library requirements from the selected checkout; install additional system packages only if actually needed and separately authorized by the normal environment controls. Upstream development helpers such as just/nextest may be useful; distinguish required tools from optional convenience tools before downloading them.

Network and package operations will use the environment's normal approval mechanism if required. Writing this plan does not itself perform those operations.

=== 3. Establish an unmodified baseline build

Fetch the official source, resolve the selected release to its commit, inspect applicable repository instructions and keep the supplied Cargo.lock. Start with the host GNU/Linux target already supported by the machine's native compiler; record this as a deliberate difference from the installed static musl package. Cross-compiling a matching musl release is a separate optional packaging task, not a prerequisite for a local color experiment.

Candidate build command from `codex-rs`, after resource checks and toolchain setup:

[source,shell]
----
cargo build --locked -p codex-cli --bin codex --profile dev-small --jobs 2 --timings
----

The wrapper will set explicit isolated cache/target paths. Lower the job count if measurements justify it. Build only this binary and its required dependencies; avoid `--workspace`, `--all-targets` and `--all-features` for this task. Use upstream feature defaults initially. Do not remove subsystems arbitrarily just to force a smaller build.

Capture stdout/stderr and timing/resource observations. Smoke-test the *unpatched* build first so compiler, packaging or runtime failures are distinguishable from our rendering change. Reuse the same target cache for the patch build; keep the unpatched executable as a comparison artifact.

If `dev-small` behavior is unsuitable for ordinary use, evaluate a separate optimized build after the visual result is accepted. Record any profile changes and their runtime consequences. A local build is not a bit-for-bit reproduction of the official release.

=== 4. Implement the smallest coherent rendering patch

Add one shared, optional user-surface color policy used by the composer and submitted-message cell. Preserve the original rendering path when disabled. Check how per-span foreground colors override inherited styles; setting only the outer block's ink is not sufficient evidence that links, mentions and dimmed text stay readable.

Use the existing terminal color-depth and contrast helpers where appropriate. Test truecolor and 256-color operation; preserve a sensible original-style fallback when color is unavailable. Explicitly exercise `NO_COLOR` / forced color modes and unknown terminal backgrounds rather than assuming that every terminal supports RGB fills.

Keep the patch limited to terminal presentation and the supporting tests. Review the complete diff for accidental changes to authentication, agent permissions, networking, tools, prompts, storage or protocol behavior. No changes in those areas are required to request a blue message surface.

=== 5. Check behavior before selecting the custom executable

* Run formatting and the relevant rendering/style tests required by the selected source's instructions. Add focused tests for color parsing, disabled fallback and contrast/style inheritance; update only the snapshots intentionally affected by the change.
* Verify `--version`, `--help`, exit status and helper/resource discovery from the packaged custom executable.
* Exercise the terminal UI in a disposable Codex home first, without copying authentication files or private conversation history into test artifacts.
* Visually inspect editable and submitted text: CZ characters, multiline wrapping, long paste, selected text, cursor, search matches, links, mentions, paths, attachment labels, empty/disabled input and ordinary dark assistant replies.
* Check that code/diff colors and relevant keyboard behavior remain as before. Include the user's actual terminal, not only a synthetic screenshot.
* Perform one small normal session only after local presentation/packaging checks pass. Reuse normal sign-in through the intended supported path; keep logs and manifests free of credentials.

Do not make a successful full-workspace test suite a prerequisite for changing a color, but follow source instructions and investigate any affected-test failures. Do not weaken or suppress failures just to obtain a green report.

=== 6. Package an explicit launcher and rollback

Install validated artifacts into a versioned user-local directory. Provide `~/.local/bin/codex-blue` as an explicit wrapper, without shadowing `/usr/bin/codex`. Verify what executable and resources it selects and how it interacts with Codex's existing daemon/version handling.

Keep the old installed CLI available throughout. Initial UI tests should not migrate or rewrite the real Codex state. Once normal use shares the user's Codex home, ordinary settings/session writes can still happen; a visual-only source diff is not a guarantee that a running application never writes state.

Rollback is to exit the custom session and invoke ordinary `codex`. Retain the last known-good custom build until its replacement passes checks. This plan does not require replacing the current running process or abandoning its session.

=== 7. Reapply after upstream upgrades

Provide a command conceptually like `rebuild-blue --version 0.166.0`, with the version always explicit. The implementation must:

. Resolve and record the requested official release commit and its declared Rust toolchain.
. Start from a clean checkout, retaining the previous good build and patch history.
. Run strict patch applicability checks before modifying source. Do not force context-mismatched hunks, use fuzzy edits or blindly replace binary bytes.
. Stop for a small patch review when upstream moves the affected rendering/configuration code. Some updates will apply directly; others need adaptation.
. Build with the release's lockfile and recorded profile, run relevant checks and package the matching resources.
. Select the new artifact only after validation. Preserve an explicit record of custom patch identity even when upstream `--version` text remains unchanged.

No update hook should automatically replace the active custom executable merely because npm upgraded ordinary Codex. Rebuilding stays an explicit operation. If upstream later provides an equivalent supported user-message color setting, prefer retiring our patch after verifying that feature.

== Safety assessment

This is a normal source-level customization of an open-source terminal application, with a narrow visual diff. It is more maintainable than editing compiled binary bytes, but it still creates a locally supported variant.

The main practical risks are build resource exhaustion, dependency/native-library build failures, readability regressions and a patch becoming incompatible with a later release. Dependency build scripts execute as the build user; a lockfile fixes dependency selection but does not make downloaded build code intrinsically harmless. Fetch from the official source, retain pins/checksums, and avoid elevated builds. No additional account or API key is needed merely to compile or test local colors.

Keeping the installed command and the validated custom package separate makes a failed build low impact on the existing installation. It does not make development risk-free or remove the normal capabilities of whichever Codex executable is eventually launched.

== Completion criteria

The plan is implemented only when the two user surfaces have readable blue paper / dark ink in Falken's actual terminal, disable/rollback works, the regular Codex command still works, tests and packaging checks are recorded, and the version-pinned reapply script succeeds on the initial release and rejects an intentionally incompatible patch context. A future release is supported only after its own build and checks; automatic compatibility across all versions is not promised.

Record actual setup/build times and peak resources in a timestamped DONE document. Repeat the resource check immediately before implementation; the 13:17 update provides sufficient headroom, while the earlier low-space condition would have required preparation or another suitable build location.
